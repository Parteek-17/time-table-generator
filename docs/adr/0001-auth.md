# ADR 0001: Authentication and how the API trusts the web app

- Status: accepted
- Date: 2026-10-21

## Context

CLAUDE.md asks for Auth.js (email + Google) with roles stored in our own database, a separate
NestJS API, and one subdomain per institute. Students will later sign in with roll number +
one-time code.

## Decision

**Sign-in happens in the web app (Auth.js v5, `next-auth@5.0.0-beta.32`).**

- Providers: email magic link (Nodemailer provider over SMTP, see ADR 0004) and Google
  (enabled only when `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` are set).
- `session.strategy = "database"` with `@auth/prisma-adapter`. Magic links need the adapter's
  verification-token table anyway, and database sessions can be revoked server-side.
- Users, accounts, sessions and verification tokens are global tables (no `institute_id`). A
  person is one `User` across institutes; what they may do comes only from `Membership` rows.
- Google accounts link to an existing user with the same email
  (`allowDangerousEmailAccountLinking`). Safe for Google because it verifies email addresses,
  and it is what an admin expects after inviting `name@college.edu`.
- `AUTH_TRUST_HOST=true` and no `AUTH_URL`, so links and redirects use the subdomain the user is
  on. The Auth.js route handler rebuilds the request URL from the Host header, because `next dev`
  passes route handlers a `localhost` URL.

**The browser never calls the API directly.** Server components and server actions in
`apps/web` call it, so there are no cross-subdomain cookies and no CORS.

```
Browser ──cookie──▶ Next.js (demo.slotwise.app)
                     │ proxy.ts: Host → x-institute-slug: demo
                     │ auth(): session → user id
                     │ mints JWT { sub: userId, iss: slotwise-web, aud: slotwise-api, exp: 5 min }
                     ▼
                    NestJS API
                     AuthGuard:   verify HS256 JWT with API_JWT_SECRET, load User
                     TenantGuard: slug → Institute, load the user's memberships,
                                  403 unless a membership reaches this institute
                     @RequirePermission + can(): what they may do
```

- The JWT carries only the user id. Memberships are loaded fresh from the database on every
  request, so a revoked role stops working immediately.
- `API_JWT_SECRET` is shared by web and API only; tokens live 5 minutes.

**Student OTP is not in Phase 0.** `OtpLoginProvider` in `packages/shared/src/auth/otp.ts` is the
interface a later Auth.js credentials-style provider will call.

## Consequences

- Google redirect URIs cannot use wildcards, so each institute subdomain must be registered in
  the Google console (`https://<slug>.slotwise.app/api/auth/callback/google`). Fine for a handful
  of institutes. **Follow-up:** a shared sign-in host (`auth.slotwise.app`) that hands the
  session back to the institute subdomain.
- Sessions are per subdomain (host-only cookies). Someone in two institutes signs in to each.
- Any email can request a magic link and gets a `User` row; without a membership they only see
  "You don't have access yet". Rate limiting sign-in requests is a TODO before launch.
- next-auth v5 is still published under the `beta` tag. It is the version Auth.js documents
  for the App Router; we pin the exact version and track its releases.
